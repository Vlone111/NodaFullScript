# Задание для агента на сервере с Grafana

Ты работаешь **только на этом сервере**. На фронтовые ноды не ходи и ничего там не меняй —
агент сбора там уже настроен и работает, метрики приходят.

## Что уже приезжает

С нод шлёт `vmagent` через `remoteWrite`. Внешние лейблы: `node` (например `EDGE1`), `address`.
Кроме обычных метрик `node_exporter` теперь приходят:

- `docker_container_running{name="..."}` — 1/0 по каждому контейнеру
- `docker_container_restarts_total{name="..."}` — счётчик перезапусков
- `probe_success`, `probe_duration_seconds` — джоб `blackbox_icmp`, цели `1.1.1.1` и `8.8.8.8`
- `probe_http_duration_seconds{phase="resolve|connect|tls|processing|transfer"}` — джоб `blackbox_http`
- `probe_ssl_earliest_cert_expiry` — оттуда же

Важно: эти пробы запущены **на самих нодах** и меряют путь «нода → интернет».
Не дублируй их blackbox-ом на этом сервере — он мерил бы другой путь.

## Задача 1. Оповещения в Telegram

1. `Alerting → Contact points → Add contact point`, тип Telegram, туда BotToken и Chat ID.
   Для группы Chat ID — отрицательное число, узнаётся через
   `api.telegram.org/bot<TOKEN>/getUpdates` после сообщения в группу.
2. Нажать **Test** и убедиться, что сообщение реально пришло.
3. Сделать этот contact point получателем по умолчанию в Notification policies.

## Задача 2. Правила алертов

Завести ровно эти. Больше не нужно: правило, на которое махнут рукой, обесценивает все остальные.

| Название | Условие | Pending period |
|---|---|---|
| Нода пропала | `up == 0` | 3m |
| Контейнер лежит | `docker_container_running == 0` | 5m |
| Путь наружу деградировал | `probe_success{job="blackbox_icmp"} == 0` | 5m |
| Сертификат кончается | `(probe_ssl_earliest_cert_expiry - time()) / 86400 < 14` | 1h |
| Диск скоро кончится | `predict_linear(node_filesystem_avail_bytes{mountpoint="/"}[6h], 4*24*3600) < 0` | 30m |
| Память на исходе | `node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes < 0.1` | 10m |
| Потери в сети | `100 * rate(node_netstat_Tcp_RetransSegs[5m]) / rate(node_netstat_Tcp_OutSegs[5m]) > 3` | 15m |
| Очередь подключений переполнена | `rate(node_netstat_TcpExt_ListenOverflows[5m]) > 0` | 5m |
| Буфер UDP переполняется | `rate(node_netstat_Udp_RcvbufErrors[5m]) > 0` | 15m |

В аннотацию каждого правила добавь `{{ $labels.node }}` — иначе из сообщения непонятно,
какая нода упала.

**Обязательно проверь, что алерт умеет сработать.** Правило `up == 0` опирается на
существование ряда: если ряд исчезнет целиком, условие может перестать вычисляться и
тишина будет выглядеть как «всё хорошо». Останови `vmagent` на тестовой ноде на 5 минут
и убедись, что сообщение пришло. Непроверенный алерт — самоуспокоение, а не мониторинг.

## Задача 3. Дашборд

Один дашборд, переменная `node` через `label_values(node)`, все запросы фильтруются
`{node="$node"}`. Панели:

1. **Доступность** — `up`, `probe_success`, тип Stat
2. **CPU** — `100 * (1 - avg by (node) (rate(node_cpu_seconds_total{mode="idle"}[5m])))`, unit Percent (0–100)
3. **Память** — `100 * (1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)`, unit Percent (0–100)
4. **Диск** — `100 * node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"}`
5. **Трафик** — `rate(node_network_receive_bytes_total{device="ens3"}[5m]) * 8` и то же для transmit, unit **bits/sec**
6. **Потери TCP** — `100 * rate(node_netstat_Tcp_RetransSegs[5m]) / rate(node_netstat_Tcp_OutSegs[5m])`, unit Percent (0–100)
7. **Фазы рукопожатия** — `probe_http_duration_seconds`, легенда `{{phase}}`, unit seconds
8. **Задержка до анкоров** — `probe_duration_seconds{job="blackbox_icmp"}`, легенда `{{instance}}`, unit seconds
9. **Контейнеры** — `docker_container_running`, легенда `{{name}}`, тип Stat

Порогов достаточно на панелях 2–4 и 6: жёлтый после 80, красный после 90
(для потерь TCP — жёлтый после 1, красный после 3).

## Чего НЕ делать

- Не ставить cAdvisor и Loki: на 4 ГБ они будут драться за память с тем, что работает.
- Не заводить алерты на `node_load1` — он одинаково растёт от занятого CPU и от повисшего
  диска, и толку от него меньше, чем от `node_pressure_*`.
- Не трогать конфиги на фронтовых нодах.
- Не привязывать ничего к панели Remnawave: мониторинг должен переживать её обновление
  и падение.

# Догрузка задания: тишина по умолчанию

Цель — чтобы в Telegram приходило только то, ради чего стоит открыть ноутбук.
Алертинг, который шумит, читать перестают, и он становится хуже отсутствующего.

## 1. Одна авария — одно сообщение

Сейчас при падении ноды сработают сразу `up`, все `docker_container_running`,
обе пробы и, скорее всего, память с диском. Это шесть-девять сообщений про
одно событие.

В notification policy выстави:

```
group_by:         [alertname, node]
group_wait:       30s      # подождать соседей перед первой отправкой
group_interval:   5m       # как часто досылать изменения по той же группе
repeat_interval:  4h       # не долбить одним и тем же чаще раза в 4 часа
```

`group_by` по `node` — ключевое: падение одной ноды схлопывается в одну карточку.

## 2. Разделить «беги чинить» и «посмотри на досуге»

Проставь каждому правилу лейбл `severity` и разведи маршруты:

| severity | Правила | Куда |
|---|---|---|
| `critical` | нода пропала, контейнер лежит, путь наружу пропал, диск скоро кончится | Telegram сразу |
| `warning` | сертификат кончается, память, потери сети, буферы, очередь подключений | Telegram, но `group_interval: 30m` и `repeat_interval: 24h` |

Правило проверки простое: **если по этому сообщению ты не встанешь ночью —
это не critical.** Сертификат с двухнедельным запасом ночью не чинят.

## 3. Поднять пороги там, где они заведомо ложные

Значения ниже измерены на живой ноде, а не взяты из головы:

| Правило | Было | Стало | Почему |
|---|---|---|---|
| Потери в сети | `> 3` | **`> 5` за 15m** | Фон на EDGE1 уже 1.09%, и он гуляет. Трёх процентов правило будет касаться регулярно без всякой аварии. |
| Буфер UDP | `> 0` | **`> 5` за 15m** | За 2.6 суток набралось 413 событий — это ровный тонкий ручеёк. Порог `> 0` превращает его в постоянный алерт. |
| Очередь подключений | `> 0` | оставить `> 0`, но pending **5m** | Здесь ноль — правильный порог: переполнение очереди всегда авария. Но короткий всплеск при рестарте пережить надо. |
| Контейнер лежит | pending 5m | **pending 10m** | Обновление панели и перезапуск ноды укладываются в 10 минут. Иначе каждый твой апдейт = алерт. |

## 4. Окно обслуживания

Заведи mute timing `maintenance` и научись включать его перед плановыми
работами. Обновление Remnawave, перезапуск ноды, пересборка сайта — всё это
штатно роняет контейнеры на минуту, и алерт про это бесполезен.

## 5. Сообщение должно быть самодостаточным

В аннотацию каждого правила:

```
{{ $labels.node }} — {{ $labels.alertname }}
значение: {{ $value }}
```

Сообщение «что-то не так» заставляет лезть в дашборд, чтобы понять, куда
бежать. Сообщение «EDGE1, диск, осталось 4%» — не заставляет.

## 6. Через неделю — ревизия

Через семь дней посмотри, какие правила срабатывали, и по каждому ответь:
предпринял ли человек действие. Те, по которым действия не было ни разу,
понизь до `warning` или удали. Это не разовая настройка, а привычка.
